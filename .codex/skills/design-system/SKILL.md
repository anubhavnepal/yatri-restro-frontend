# Design System

## When to use this skill

- When defining reusable UI primitives, tokens, spacing rules, or typography patterns.
- When reviewing whether new components fit the existing brand system.
- When creating consistency across sections, forms, menus, drawers, and CTA treatments.

## Project-specific rules

- Mobile-first design.
- Premium dark luxury aesthetic.
- Elegant spacing and typography.
- Accessible contrast and focus states.
- Clear CTAs.
- Smooth but subtle animation.
- Avoid heavy WebGL, particles, excessive motion, or performance-heavy visual effects.
- Keep design tokens practical for Tailwind-driven implementation.
- Favor a small, strong component language over a sprawling component inventory.
- Make reusable patterns work for English and Japanese content lengths.
- Ensure states such as hover, focus, loading, empty, error, and disabled are defined consistently.

## Expected output quality

- Produces a system that feels deliberate, premium, and implementation-ready.
- Reduces visual drift across the app.
- Makes future feature work faster without creating unnecessary abstraction layers.
- Supports accessibility, localization, and performance from the system level.

## Things to avoid

- Overengineering a design system before the product needs it.
- Creating too many one-off variants with unclear purpose.
- Picking token names that are hard to scale or understand.
- Ignoring multilingual layout pressure.
- Sacrificing accessibility for aesthetics.

## Checklist before completing work

- Confirm the system supports the premium restaurant brand direction.
- Confirm typography, spacing, color, and component states are consistent.
- Confirm reusable patterns remain mobile-first and accessible.
- Confirm the system works for English and Japanese text.
- Confirm the proposal avoids unnecessary abstraction.
